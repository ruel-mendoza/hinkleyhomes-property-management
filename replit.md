## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `SUPABASE_DATABASE_URL` — Supabase session pooler connection string (`DATABASE_URL` is reserved by Replit and not used)
- Integration env: `COHO_API_KEY`; Xero `XERO_CLIENT_ID`, `XERO_CLIENT_SECRET`, `XERO_REDIRECT_URI`, `XERO_TOKEN_ENCRYPTION_KEY` (optional `XERO_SCOPES`, `XERO_WEBHOOK_KEY`). All names and formats are documented in `.env.example`; values go in Replit Secrets. The API server logs which integrations are configured at startup.

- COHO actions mirror: `coho_actions` in Supabase, filled by `syncCohoActions` (artifacts/api-server/src/lib/coho-actions-sync.ts). Runs from the Actions page (Sync now, or automatically when data is >5 min old) and every 15 min from n8n (`n8n/coho-actions-sync.workflow.json` → `POST /api/integrations/coho/actions/sync`, header `X-Hinkley-Sync-Key` = `PMS_SYNC_KEY`). Runs are logged in `integration_sync_runs` with trigger `actions:*`. Changes made on the Actions page (status, assign, snooze, edit/create custom actions) go to COHO first, then the action is re-read into `coho_actions` and written to `audit_log` with the staff email. COHO accepts action statuses only as SCREAMING_SNAKE (`IN_PROGRESS`), although it returns camelCase.

- Properties page (`/properties`): `GET /api/properties` merges live COHO properties, open-action counts from `coho_actions`, and register-only properties from Supabase `properties` (added with New property; COHO has no create-property API, so staff add them in COHO too). Buildings live in `buildings` / `building_properties`. Group companies are in `entities` (5 Xero orgs seeded with `pnpm --filter @workspace/db run seed:entities`).
- Website widget: public page `/widget` (no sign-in) reads `GET /api/public/listings`, which lists only properties with a room free, by street, town and postcode area, never house numbers. Cached 5 min.
- Occupancy page (`/occupancy`): `GET /api/occupancy` joins COHO units (`/properties?includeRooms=true`), current and future tenancies (`/tenancies`) and rent review (`/rent-review/tenancies`, for rent and fixed-term end). Dates are converted to UK dates; only tenant names leave the server. "Becoming periodic" = fixed term ending within 60 days (our choice; COHO doesn't expose its window).
- Operations overview money section: `GET /api/overview/money` (cached 5 min) reads COHO rent collection, credit control, deposits and rent review, and Xero banking per company through the n8n gateway (unreconciled bank transactions; balances from `Reports/BankSummary`). Company notes for Management and Stays (no property money) live in `artifacts/api-server/src/routes/money.ts`. Bank Summary accounts are classed as bank, card (Xero `BankAccountType` CREDITCARD) or payment platform (Stripe, PayPal, GoCardless, Telleroo by name); the bank total counts real bank accounts only, and companies whose summary mixes in cards or platforms (or a platform holding £10k+) get notices shown at the top of the overview for the accounts team.
- n8n Xero gateway reports: report resources (`profitAndLoss`, `balanceSheet`, `agedPayables`, `bankSummary`) go through the "Call Xero (reports)" node, which needs a separate n8n OAuth2 credential "Xero reports" with scope `accounting.reports.read` (the built-in "Xero account" credential lacks it, so reports return 401). Everything else still uses "Xero account".
- Performance page (`/performance`): `GET /api/performance` (COHO data cached 1 h, ~25 COHO calls per load) works out rent roll vs target (sum of advertised unit rents), rent paid on time (`paymentStatus` on per-unit rent due records), days late, tenant satisfaction and occupancy, matching COHO's Rent Roll page. COHO's API returns no ended tenancies, so occupancy history, tenancy length and days to fill voids come from `coho_unit_snapshots` (one row per unit per UK day). A snapshot is saved when the page is opened and daily by n8n (`n8n/coho-unit-snapshot.workflow.json` → `POST /api/integrations/coho/unit-snapshot`, header `X-Hinkley-Sync-Key`). After pulling, run `pnpm --filter @workspace/db run push` to create the table.
- Compliance page (`/compliance`): `GET /api/compliance?status=expired|due_30|due_60|due_90|not_started|not_required|all` (cached 10 min) counts items per type from one COHO `/compliancy/overview?groupByProperty=true` call per bucket, and fills Carried Out / Expiry from each listed property's record overviews (cached 30 min; skipped for "not started"/"not required" rows, which have no record). The sidebar link shows the expired count. COHO dates are UK midnight stored in UTC, so `lib/coho-compliance.ts` reads them in Europe/London time (UTC dates were a day early during BST).
- Finance group (cached 30 min, read-only from COHO): Rent & fees (`/finance`, `GET /api/finance/income`) groups COHO `/finance/financial-items` (rent = client money, management fee = Hinkley income; COHO holds no expenses here, those are in Xero) by month, property and owner; Rent bank feed (`/bank-feed`, `GET /api/finance/bank-feed`) lists COHO `/transactions/items?transactionFilterStatus=all` as matched / unmatched / excluded, with account numbers reduced to the last 4 digits on the server. The overview's money-trend card charts rent per month and the matched share of the bank feed. Charts use Recharts via `components/charts/MonthlyBars.tsx` (blue #3987e5 / orange #d95926, validated on the #192538 panel).
- Possible rent payments: `lib/rent-matching.ts` pairs each overdue tenancy (COHO credit control) with an unmatched rent-feed bank line for exactly the outstanding amount, received from 7 days before the due date to today (each line used once). Shown on the bank feed ("Possible rent") and against arrears on the overview. COHO's own match suggestions, match rules, rent automation status and pending transactions are not in its API, so matching is still done in COHO. The bank feed's Reconcile panel lays each proposal out like COHO (bank line → proposed rent, with a plain-English reason) and links to COHO via `VITE_COHO_TRANSACTIONS_URL` (default https://app.coho.life); COHO's API has no endpoint to link a bank line to rent.
- Invoices page (`/invoices`, Xero Phase 1, read-only towards Xero): `GET /api/receivables` (cached 10 min) reads open sales invoices (`Type=="ACCREC"`, AUTHORISED, AmountDue>0) and bills (`ACCPAY`, AUTHORISED/SUBMITTED) for all five companies through the gateway, with aging buckets and a flag when a rent invoice matches a COHO property (rent tracked in both systems). Follow-ups (outcome, next chase date, promised date, notes) live in Supabase `xero_invoice_follow_ups` / `xero_invoice_follow_up_notes` and are audit-logged; nothing is sent to Xero or customers. "Copy payment link" uses the gateway's `onlineInvoice` resource (Xero `/Invoices/{id}/OnlineInvoice`). After pulling: `pnpm --filter @workspace/db run push` and re-paste `n8n/xero-gateway.workflow.json` into the n8n gateway workflow.
- Payment reminders (Phase 2): the app decides, n8n sends. `lib/xero-reminders.ts` picks the next stage per overdue invoice (one stage at a time; skips companies switched off, paused, disputed, promised, write-off review, "says paid", staff chases and Xero reminders within the cooldowns, and invoices older than the limit with no reminder yet). Settings (`xero_reminder_settings`, one row) default to automatic reminders OFF and TEST mode (all mail to the internal address); change them on the Invoices page (audit-logged). Every send is logged in `xero_invoice_reminders`; live sends also add a follow-up note.
- Finance checks page (`/checks`): the app is the only reader of Xero. `runDailyChecks` (artifacts/api-server/src/lib/finance-checks.ts) ranks overdue invoices and bills by value, age and risk (`lib/overdue-ranking.ts`) and tracks new / more urgent / cleared items in `xero_overdue_tracking`; fetches supplier bills changed since the last run (13 months on the first run) into `xero_bill_history` and runs the price and bank checks (`lib/bill-checks*.ts`); and runs supplier / expense-category / recurring-bill spend trends (`lib/spend-trends.ts`). Findings go to `exception_queue` (raised once per bill or month), runs to `integration_sync_runs` (trigger `xero_daily_checks:*`, counts in `details`). Started daily by n8n (`n8n/xero-daily-checks.workflow.json` → `POST /api/integrations/xero/daily-checks`, header `X-Hinkley-Sync-Key`) or by "Run checks now". Staff API: `GET /api/checks/overdue`, `GET|PUT /api/checks/alerts`, `GET /api/checks/reminders`, `GET|POST /api/checks/runs`. Nothing is emailed; the OneDrive CSV files of the old workflow are no longer used.
- Bill coding (Finance checks > Bill coding, n8n `n8n/bill-coding.workflow.json`, "Route A v11", hourly): the app picks draft/submitted supplier bills through the gateway (`GET /api/integrations/bill-coding/plan`), n8n downloads each bill's file, asks for a saved reading (`GET /api/integrations/bill-coding/readings/:hash`, table `document_readings`), reads new files with OpenAI and posts the reading (`POST /api/integrations/bill-coding/review`). The app (lib/bill-coding.ts, rules in lib/bill-coding-rules.ts) runs the bank and price checks, matches each line to a Xero company + Property tracking option, and records `bill_coding_reviews` (held / shadow_planned / pending_xero / created_draft / updated_draft / create_failed / not_invoice / read_failed). When shadow mode is off it returns the draft bills for n8n to write, and n8n reports each result (`POST /api/integrations/bill-coding/result`). Settings live in `bill_coding_settings` (shadow mode on by default). Held lines are answered in the app and saved as `property_aliases` rows of kind `line`; spellings (kind `text`) are managed on the Property aliases page (`/property-aliases`, CRUD under `/api/property-aliases`, audit-logged). `property_aliases` now points either at a register property or at `xero_tenant_id` + `xero_tracking_option` (or `overhead`). No emails and no OneDrive CSV files. Company names as written on invoices ("EDJ Investments Ltd" = Holdings) live in `company_aliases` (Property aliases page, "Company names" tab, `/api/company-aliases`); bill coding notes an invoice addressed to a different company from its bill. The old Route A CSV files are imported with `pnpm --filter @workspace/db run import:route-a` (files in the git-ignored `import/` folder; safe to re-run).
- n8n workflow `n8n/xero-overdue-reminders.workflow.json` (v5): payment reminders only; the daily digest, cost-increase alerts and their data tables moved into the app (Finance checks). Reminders come from `GET /api/integrations/xero/reminders/plan` and each result goes to `POST /api/integrations/xero/reminders/result` (header `X-Hinkley-Sync-Key`). Its "PMS: run action" webhook (header `X-Hinkley-Gateway-Key`, URL in `N8N_REMINDER_WEBHOOK_URL`) handles Chase now, re-send from Xero and Xero notes. The gateway also allows `invoiceHistory` and `invoiceReminderSettings` (read-only) so reminders wait after Xero's own.
- Xero reminder opt-outs: Xero's per-invoice "Reminders: Turned off" setting is not in its API, so the app reads the invoice History for the latest reminders off/on change (needs the gateway's `invoiceHistory`), and also treats any customer in a Xero contact group whose name contains "No reminders" as opted out. Both stop automatic reminders and show on the Invoices page.
- Invoices > For review (`/invoices?tab=review`): only open reviews are kept in `invoice_intake_reviews`. Done / Dismiss (`POST /api/invoices/intake-reviews/:id/resolve`) deletes the row and writes a summary, outcome, note and staff email to `audit_log`. `clearResolvedIntakeReviews` (lib/intake-reviews.ts) also deletes an open review when Xero already has the bill: same invoice number (ignoring case, spaces, punctuation and leading zeros) plus the same supplier or total, looked up in `xero_bill_history` (not voided/deleted) and `bill_coding_reviews` (drafts). It runs when the list or overview is read (at most once a minute) and after the daily checks. An email whose review was resolved is not re-added by `POST /api/integrations/intake/review`; n8n itself skips emails already in `invoice_intake_checks`.
- Stays page (`/stays`, Hinkley Homes Stays): short-stay bookings mirrored **read-only** from Smoobu, the channel manager and source of truth for serviced accommodation (PriceLabs sets prices and stay rules through it, so the app never writes bookings, rates or availability). Smoobu reads go through the n8n gateway when `N8N_SMOOBU_GATEWAY_URL` is set (`n8n/smoobu-gateway.workflow.json`, header `X-Hinkley-Gateway-Key`, same key as the Xero gateway unless `N8N_SMOOBU_GATEWAY_KEY` is set): the app sends `{ path, query }`, n8n allows only the read paths the app uses (apartments, reservations, price elements, threads), calls Smoobu with the old-key credential or, with Settings > `useSignedKey` on, signs with n8n Variables `SMOOBU_API_KEY` / `SMOOBU_API_SECRET`, and answers `{ ok, status, retryAfter, data }`. Without the gateway, `lib/smoobu-api.ts` signs every GET with HMAC when `SMOOBU_API_SECRET` is set, and otherwise sends the old `Api-Key` header with `SMOOBU_API_KEY` (Smoobu switches that off on 31 Oct 2026; the startup log says which is in use). `n8n/smoobu-get-all-bookings.workflow.json` has the same switch (Settings > `useSignedKey`). `lib/stays.ts` saves apartments to `smoobu_apartments` and bookings to `short_stay_bookings` (blocked dates skipped, guest name only), and sets `cleaning_allowances` to the guest cleaning fee (Smoobu price element `cleaningFee`) per booking. Smoobu webhooks go to n8n (`n8n/smoobu-sync.workflow.json`, secret webhook path) which forwards them to `POST /api/integrations/smoobu/event`; the app re-reads the booking from Smoobu rather than trusting the payload. The same workflow calls `POST /api/integrations/smoobu/sync` hourly (bookings modified since the last good run; the first run covers departures from 120 days back), logged in `integration_sync_runs` with trigger `bookings:*`. The summary tiles at the top of Stays are buttons: arriving today, leaving today, in house and not ready to arrive filter the Bookings table (same rules as the server's counts; click again or **Show all** to clear) and scroll to it; guest conversations today scrolls to the messages panel. Latest guest messages come live from Smoobu `/api/threads` (cached 2 min, cleared on `newMessage`): the newest 8 conversations with the latest message text, a count of conversations with a message today, and Smoobu's account-wide unread total in the caption. Smoobu returns threads newest first, 25 a page, with no unread count or sender per thread. Properties page tab **Smoobu apartments** (`/properties?tab=smoobu`, `SmoobuApartmentsTab.tsx`) lists every Smoobu apartment beside the COHO and register properties, with size, whether a guest is in tonight and the next arrival; staff link each one to the property it is in (`smoobu_apartments.coho_property_reference` or `.property_id`, one or the other; audit-logged as `smoobu_apartment.link`/`unlink`; changes only this app, never Smoobu). Every sync (and the tab's **Link automatically** button, `POST /api/stays/apartments/auto-link`) links apartments nobody has linked or unlinked yet (`linked_by` null) when exactly one COHO or register property matches: the apartment name first, then its street, normalised like property aliases (`aliasKey`) and compared with the property name, house number + street, address line and text aliases; postcodes must agree when both are known, and a spelling without a house number needs matching postcodes. Two or more matches are left for staff. Auto links are marked `linked_by = auto` (shown as "Matched automatically") and audit-logged as `smoobu_apartment.auto_link`; any staff choice sets `linked_by = staff`, so it is never auto-matched again. Bookings get `property_id` from that link (through the register row for a COHO reference, when there is one), falling back to the older `properties.smoobu_property_id`. Staff API: `GET /api/stays`, `POST /api/stays/sync`, `GET /api/stays/apartments`, `PUT /api/stays/apartments/{apartmentId}/link`. Overview shows the Stays strip, with an Apartments link and a count of apartments not linked. After pulling: `pnpm --filter @workspace/db run push`.
- ChargeAutomation guest checks (Stays): Smoobu sends bookings to ChargeAutomation, which runs online check-in, ID, card and deposit checks and takes guest payments. The app is **read-only** towards it and never re-syncs bookings, properties or rentals from it (Smoobu already has them). ChargeAutomation webhooks go to n8n (`n8n/chargeautomation-events.workflow.json`, secret webhook path) which forwards them to `POST /api/integrations/chargeautomation/event` (`X-Hinkley-Sync-Key`). `lib/guest-checks.ts` keys each event by `pms_booking_id`, or else ChargeAutomation's own booking id (for bookings from Smoobu both are the Smoobu booking id, and its `property_id` is the Smoobu apartment id; `external_id` is empty) into `guest_checks` (online check-in time, ID / card / deposit outcome and hold amount, latest payment outcome; no documents, contacts or card data), sets `short_stay_bookings.charge_automation_reference`, and upserts payment events into `payments` (source `charge_automation`, external id = `charge_ref_no`; Xero stays the ledger). Online check-in is confirmed by re-reading the booking through the n8n gateway (`n8n/chargeautomation-gateway.workflow.json`, `N8N_CHARGEAUTOMATION_GATEWAY_URL`, same header key as the Xero gateway): it logs in with n8n Variables `CHARGEAUTOMATION_API_KEY` / `CHARGEAUTOMATION_API_SECRET` (OAuth client id and secret, 24-hour token kept in workflow static data) and allows only GET one booking, the booking list and a payment request. Every Stays sync also reads ChargeAutomation's booking list (check-ins from 14 days back to 7 ahead, 25 a page) for `pre_checkin_completed`, so online check-in shows without waiting for a webhook; payments, deposits, ID and card checks only come by webhook. Stays shows a Guest checks column and "not ready to arrive" (arriving today or tomorrow with a failed payment, deposit, ID or card check, or no online check-in) once the gateway is set up or any event has arrived; the Overview strip shows the count.
- Staff presence: the app sends `POST /api/presence/heartbeat` about once a minute (and on page change and tab show/hide); `staff_presence` keeps one row per staff member with the page name only (never search or filters). Online = seen in the last 2.5 min with the tab in front; Away = tab hidden or seen in the last 10 min; the top-bar indicator lists everyone seen in the last 30 days. Needs `pnpm --filter @workspace/db run push` once.
